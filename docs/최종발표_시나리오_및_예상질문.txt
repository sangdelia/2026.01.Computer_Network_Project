▶ 슬라이드 6 — OSI 계층 매핑  [빠르게 — 표만 훑기]
OSI 7계층 (네트워크 통신을 7단계로 나눈 표준 모델)을 실제 구현에 1:1 매핑했습니다.
응용은 REST API, 표현은 JSON·UTF-8,
세션은 JWT HttpOnly 쿠키 (중간발표 때 localStorage에서 보안 강화된 방식으로 전환),
전송은 TCP 포트, 네트워크는 IP·Cloudflare, 하위 계층은 하드웨어가 담당합니다.

▶ 슬라이드 8 — REST API 설계  [빠르게]

▶ 슬라이드 9 — TCP 커넥션 풀  [빠르게]

[OSI / 네트워크 개념]

Q. 세션 계층을 중간발표 때는 localStorage, 지금은 JWT 쿠키로 바꾼 이유가 있나요?
A. localStorage는 JavaScript로 직접 접근이 가능해 XSS 공격에 취약합니다.
   (XSS: 악성 스크립트를 삽입해 다른 사용자의 데이터를 탈취하는 공격)
   JWT를 HttpOnly 쿠키에 저장하면 JavaScript에서 읽을 수 없어 토큰 탈취가 차단됩니다.
   세션 유지라는 역할은 동일하지만 보안 수준이 높아졌습니다.

Q. TCP와 UDP 중 왜 TCP를 선택했나요?
A. 데이터베이스와의 통신에서는 데이터 무결성이 중요합니다.
   TCP는 3-way handshake와 재전송 보장으로 신뢰성 있는 전달을 보장합니다.
   의견이나 반응 데이터가 손실 없이 저장되어야 하기 때문에 TCP를 사용했습니다.

Q. 3-way handshake가 무엇인가요?
A. TCP 연결을 맺는 과정입니다.
   클라이언트가 SYN을 보내고, 서버가 SYN-ACK로 응답하고,
   클라이언트가 ACK로 확인하는 3단계입니다.
   이 과정이 끝나야 실제 데이터 전송이 시작됩니다.

Q. 패킷 교환이란 무엇인가요?
A. 데이터를 일정 크기의 패킷으로 나눠서 각자 독립적인 경로로 전송한 뒤
   목적지에서 재조립하는 방식입니다.
   회선 교환과 달리 경로를 점유하지 않아 효율적입니다.
   Cloudflare Tunnel도 이 패킷 교환 방식으로 노트북의 데이터를 엣지 서버까지 전달합니다.

[HTTP / API 설계]

Q. REST API가 무엇인가요?
A. HTTP 메서드(GET·POST·PATCH·DELETE)와 URL로 자원을 표현하고 조작하는 설계 방식입니다.
   예를 들어 GET /api/opinions는 의견 목록 조회,
   POST /api/opinions는 의견 작성처럼
   메서드와 URL만 보고도 의도를 알 수 있게 설계했습니다.

Q. PUT 대신 PATCH를 쓴 이유가 있나요?
A. PUT은 리소스 전체를 교체하고, PATCH는 일부만 변경합니다.
   의견 수정 시 summary와 content만 바꾸고 나머지 필드는 유지해야 하므로
   PATCH가 더 적합합니다.

Q. 401과 403의 차이는?
A. 401은 인증 실패(누군지 모름), 403은 인가 실패(누군지는 알지만 권한 없음)입니다.
   미로그인 상태에서 요청하면 401,
   로그인은 됐지만 타인 게시물을 수정하려 하면 403을 반환합니다.

[구현 관련]

Q. JWT가 무엇인가요?
A. JSON Web Token의 약자로, 서버가 사용자 정보를 담아 서명한 토큰입니다.
   서버는 DB 조회 없이 토큰 서명만 검증해 사용자를 식별할 수 있어 빠릅니다.
   이 프로젝트에서는 로그인 시 발급해 HttpOnly 쿠키에 저장하고 7일간 유지합니다.

Q. bcrypt가 무엇인가요?
A. 비밀번호를 단방향으로 해싱하는 알고리즘입니다.
   같은 비밀번호라도 매번 다른 해시가 나오고(salt 추가),
   해시에서 원본을 복원할 수 없습니다.
   DB가 유출되더라도 실제 비밀번호는 알 수 없습니다.

Q. AI 주제 자동 생성은 어떻게 구현했나요?
A. OpenAI GPT-4o-mini API를 사용합니다.
   서버가 시작될 때 node-cron으로 스케줄러를 등록하고,
   매일 낮 12시에 전날 주제를 비활성화한 뒤 새 주제 5개를 자동 생성해 DB에 저장합니다.
   중복 방지를 위해 최근 30개 주제를 프롬프트에 포함해 요청합니다.

Q. Cloudflare Tunnel URL이 매번 바뀌는 건 불편하지 않나요?
A. Quick Tunnel은 임시 용도라 매번 바뀝니다.
   Named Tunnel로 전환하면 고정 도메인을 사용할 수 있습니다.
   현재는 발표 시연 직전에 터널을 열고 QR을 공유하는 방식으로 운영합니다.

Q. 1인 1반응은 어떻게 보장하나요?
A. reactions 테이블에 (opinion_id, user_id) 복합 UNIQUE 키를 설정했습니다.
   DB 레벨에서 중복 INSERT를 차단하기 때문에
   애플리케이션 로직과 무관하게 물리적으로 1인 1반응이 보장됩니다.

Q. PM2가 무엇인가요?
A. Node.js 프로세스 관리 도구입니다.
   서버가 예외로 종료되면 자동으로 재시작하고,
   로그를 파일로 저장하며 CPU·메모리 사용량도 모니터링할 수 있습니다.
   발표 중 서버가 다운되는 상황을 방지하기 위해 적용했습니다.
